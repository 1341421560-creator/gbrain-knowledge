<a id="core-conclusions"></a>
## 1. 核心结论

- VPN 故障要先区分是否有握手、是否有双向流量、IP 是否通、DNS 是否通和出口 IP 是否正确。
- VNC 故障要先确认服务端 VNC 是否启动、SSH 隧道是否保持打开、Viewer 端口是否填对。
- 64.83.43.228 的 RDP 滚动与拖窗卡顿，按会话实际协商的编码、分辨率和操作反馈核对。已实测改善的组合是 RFX Progressive、1280×720 与原代理路径。
- 线路慢不一定是服务器出口慢；当前实测服务器到公共 DNS 很快，主要瓶颈在本机到马来西亚服务器入口线路。

<a id="scope"></a>
## 2. 适用范围

- **适用对象：** 当前 VPS、VNC、64.83.43.228 的 xrdp 远程桌面、AmneziaWG、client2、Clash Verge/Mihomo。
- **适用场景：** 能连接但没网、找不到配置、速度慢、远程桌面失败。
- **不适用场景：** 硬件故障、服务商大规模故障或未知第三方客户端 bug。

## 3. 故障排查

<a id="section-vnc-连接不上"></a>
### VNC 连接不上

#### 故障现象

TigerVNC 显示无法连接 `127.0.0.1::5901` 或 `127.0.0.1::5902`。

#### 可能原因

1. 服务器 VNC 没启动。
2. Windows SSH 隧道窗口关闭。
3. Viewer 端口填错。
4. VNC 密码对应错用户。

#### 排查顺序

服务器查看端口：

```bash
ss -ltnp | grep 590
```

查看进程：

```bash
ps -eo user,pid,ppid,cmd | grep -E 'Xtigervnc|vncserver|xfce4-session' | grep -v grep
```

#### 解决方法

root：

```bash
cd /root/Desktop/output/vnc_tools
./start-vnc.sh
```

cr：

```bash
cd /home/cr/vnc_tools
./start-vnc-cr.sh
```

<a id="section-amneziawg-能连接但没流量"></a>
### AmneziaWG 能连接但没流量

#### 故障现象

客户端显示已连接，服务器能看到 handshake，但网页打不开或没有出网。

#### 可能原因

1. UFW 默认 `deny (routed)`，缺少 `awg0` 转发规则。
2. NAT 没有覆盖 `10.66.66.0/24`。
3. 客户端包含 `::/0`，服务器没有 IPv6 转发。

#### 排查顺序

```bash
awg show awg0
sysctl net.ipv4.ip_forward
iptables -t nat -S | grep 10.66.66
ufw status verbose
```

#### 解决方法

历史修复规则：

```bash
ufw route allow in on awg0 out on eth0
ufw route allow in on eth0 out on awg0
```

客户端只保留 IPv4：

```ini
AllowedIPs = 0.0.0.0/0
```

<a id="section-client2-连接后本机没网"></a>
### client2 连接后本机没网

#### 故障现象

服务器看到 client2 有握手和流量，但客户端网页打不开。

#### 可能原因

1. DNS 不通。
2. MTU 过大导致断流。
3. 客户端路由没有正确接管。

#### 排查顺序

客户端运行：

```powershell
ping 1.1.1.1
nslookup google.com 1.1.1.1
curl https://ifconfig.me
```

#### 解决方法

client2 稳定配置：

```ini
DNS = 1.1.1.1, 8.8.8.8
MTU = 1280
AllowedIPs = 0.0.0.0/0
```

<a id="section-clash-verge-导入后找不到配置"></a>
### Clash Verge 导入后找不到配置

#### 故障现象

把 YAML 放进配置目录后，Clash Verge 订阅页仍不显示。

#### 可能原因

Clash Verge 的配置列表由 `profiles.yaml` 管理，运行中的程序还可能把内存状态写回文件，覆盖手工条目。

#### 解决方法

优先使用界面拖拽导入。手工方式需要放入：

```text
C:\Users\AI454\AppData\Roaming\io.github.clash-verge-rev.clash-verge-rev\profiles
```

并注册到：

```text
C:\Users\AI454\AppData\Roaming\io.github.clash-verge-rev.clash-verge-rev\profiles.yaml
```

配置是否被 Mihomo 接受，可用 Mihomo 测试命令验证。

<a id="section-浏览器或-vnc-太卡"></a>
### 浏览器或 VNC 太卡

#### 故障现象

服务器 VNC 里打开 Firefox/Epiphany 卡顿，网页响应慢。

#### 可能原因

1. VPS CPU 和内存较低。
2. 浏览器和图形桌面消耗高。
3. VNC 画面传输叠加跨境延迟。

#### 解决方法

- 用 Playwright headless 代替图形浏览器。
- 减少 VNC 桌面操作。
- 使用轻量浏览器。
- 降低分辨率和标签页数量。

<a id="xrdp-scroll-drag-latency"></a>
### 64.83.43.228 的 xrdp 滚动网页和拖窗卡顿

**现象。** 网页滚动和窗口拖动时画面更新慢。初始环境是 Ubuntu 软件源的 xrdp 0.9.17，Windows 会话未协商到现代 GFX 编码。20 次 ICMP 测试均收到响应，57～65 毫秒，平均 59.2 毫秒。初始采样有约 1.4 GB 可用内存，没有持续换页。部分 CPU 采样的 steal 为 3%～16%，宿主机调度可能造成间歇抖动。

| 测试 | 结果 |
|---|---|
| 让这台服务器的 SSH 22 端口走直连 | 测量未显示稳定改善，之后观察到明显重传，已恢复原代理路径。 |
| 升级后试用 H.264 | 会话日志确认实际启用，用户试用后反馈更卡，已关闭。 |
| RFX Progressive、1280×720 和原代理路径 | 日志确认会话协商到 GFX RFX Progressive，屏幕记录显示 1280×720。用户重新登录试用后反馈“这次比原来流畅了”。 |

**最终配置。** xrdp 0.10.6.1、xorgxrdp 0.10.5，32 位色深，服务端捕获间隔 33 毫秒，目标约 30 帧每秒。服务端只监听 `127.0.0.1:3389`，Windows 通过本机 `127.0.0.1:13389` 的 SSH 隧道访问。新版运行目录为 `/opt/remote-browser-20261103/runtime/xrdp-modern`，服务由 systemd 覆盖配置指向该目录。日志报告的生效编码配置为 `/etc/xrdp/gfx.toml`，其中 `order = ["RFX"]`。

**复查顺序。** 先从[现有 RDP 入口](操作指南.md#remote-browser-rdp-648343228)重连，再核对最新会话日志是否出现 `Matched RFX mode` 和 `starting gfx rfx pro codec session`，确认当前分辨率为 1280×720，最后在同一网页重复滚动和拖窗。区分 ICMP RTT、RDP 建连应答时间和滚动体验。RDP 建连应答时间包含服务端调度，33 毫秒是捕获配置，均不能换算为实测滚动帧率。最终同时调整了编码、分辨率和线路，无法单独归因各因素的改善幅度。

**复查证据。** 项目 `output/20261103_remote_browser_optimization/` 中的 `优化记录.txt`、`final-verification.txt` 和 `proxy-route-restored.json` 对应最终状态。 `proxy-rule-verification.json` 对应此前的直连试验。

<a id="chatgpt-linux-ibus-relaunch"></a>
### ChatGPT 已装 IBus 但按 Ctrl + 空格仍无法输入中文

**现象。** 64.83.43.228 的 XFCE 会话已经运行 IBus。输入法自检能将 `nihao` 转成「你好」，但用户在服务器的 ChatGPT 输入框里按 `Ctrl + 空格` 仍打不出中文。

**诊断。** 核对当前 ChatGPT 主窗口的进程启动时间，确认它早于输入法配置。旧进程已加载 GTK 3，当时的进程映射中没有 `im-ibus.so`。IBus 后台可运行，应用需要通过 GTK 的 IBus 模块才能接收拼音候选。

1. 在 `browser` 的图形会话中运行 `ibus engine` 和 `ibus list-engine`，确认引擎列表包含 `libpinyin`。在 XFCE 用 `xfconf-query -c xsettings -p /Gtk/IMModule` 核对模块设置为 `ibus`。
2. 通过 X11 窗口的 `_NET_WM_PID` 找到当前 ChatGPT 主进程。可查看 `/proc/<PID>/maps` 中的 `im-ibus.so` 和 `libibus-1.0.so`。新应用窗口出现后给渲染器一些初始化时间，再看库是否加载。Chromium 主进程的 `/proc/<PID>/environ` 可能显示不完整，交叉核对库映射、相关子进程环境和输入框表现。
3. 保存未提交的内容后，**完整退出 ChatGPT**，再双击服务器桌面的 **ChatGPT** 图标。旧进程退出后，带 IBus 环境的快捷方式会启动新进程。
4. 在新窗口的输入框按 `Ctrl + 空格` 切到拼音，输入 `nihao` 并查看是否出现中文候选。也可用桌面 IBus 指示器切换到 **Intelligent Pinyin**。

**验证结果。** 2026-11-06 已确认新进程映射 `im-ibus.so` 与 `libibus-1.0.so`，相关子进程带有 IBus 环境变量，当前引擎可切换到 `libpinyin`。用户在重开的 ChatGPT 输入框实测确认能看到中文候选。 [IBus 与快捷方式配置](操作指南.md#xfce-ibus-libpinyin)

<a id="section-ssh-指定私钥后仍要求输入密码"></a>
### SSH 指定私钥后仍要求输入密码

#### 故障现象

Windows PowerShell 执行：

```powershell
ssh -i ".\codex_ed25519" cr@187.127.123.84
```

结果出现：

```text
WARNING: UNPROTECTED PRIVATE KEY FILE!
Permissions are too open.
This private key will be ignored.
cr@187.127.123.84's password:
```

#### 原因

这不是 `cr` 密码问题，而是本机私钥文件权限太开放。OpenSSH 忽略私钥后才退回密码登录。当前 `cr` 没有设置 Linux 密码，因此不能靠输入密码解决。

#### 修复

```powershell
$path = ".\codex_ed25519"
$me = "$env:USERDOMAIN\$env:USERNAME"
icacls $path /inheritance:r
icacls $path /remove:g "DESKTOP-5P7UDUM\CodexSandboxUsers" "Users" "Authenticated Users" "Everyone"
icacls $path /grant:r "$($me):(R)"
ssh -i ".\codex_ed25519" cr@187.127.123.84
```

<a id="section-服务器-连不上-的分层检查"></a>
### 服务器“连不上”的分层检查

先检查端口，再检查密钥登录。端口通不代表账户认证一定成功；账户认证成功才说明 SSH 登录链路完整。

```powershell
Test-NetConnection 187.127.123.84 -Port 22
ssh -o BatchMode=yes -o ConnectTimeout=15 -i ".\codex_ed25519" cr@187.127.123.84 "whoami; pwd; id"
```

历史验证结果：`22` 端口通，`cr` 登录成功，当前目录 `/home/cr`。

<a id="section-vnc-端口和-ssh-用户混淆"></a>
### VNC 端口和 SSH 用户混淆

#### 故障现象

以为“用 cr 登录就要把 `5901` 改成 `5092` 或 `5902`”。

#### 结论

SSH 用户和 VNC 端口是两个维度：

- `root@187.127.123.84` 或 `cr@187.127.123.84` 决定用哪个 Linux 账户建立 SSH 隧道。
- `5901` 或 `5902` 决定隧道转发到哪个 VNC display。

当前约定：root VNC 用 `5901`，cr VNC 用 `5902`。`5092` 是错误端口写法。
