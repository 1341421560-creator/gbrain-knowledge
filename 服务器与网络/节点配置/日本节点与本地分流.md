## 1. 核心结论

- 日本代理服务器公网 IP 为 64.83.41.3，属于敏感基础设施信息，但它本身不是登录凭证。
- Xray 在服务器上监听 TCP 443，同一个入站端口可以同时服务多位用户；用户通过不同 UUID 区分，不需要每位用户单独占一个端口。
- REALITY 私钥只保存在服务器；客户端 YAML 需要服务器 IP、UUID、REALITY 公钥、short-id、SNI 等连接参数，但这些参数不赋予 root、SSH、VNC 或文件系统权限。
- 用户 1、用户 2、用户 3 应分别使用独立 UUID 和独立 YAML。服务地址、端口、REALITY 公钥、SNI 等公共参数可以相同。
- 用户 2 原定的自动到期任务已取消；截至 2026-08-10，其用户条目仍在 Xray 中，定时器为 disabled 且 inactive。
- 三份本地 YAML 当前使用相同分流逻辑：国内和局域网优先 DIRECT，未命中流量最后由 MATCH,PROXY 交给日本节点。
- Clash Verge 通过界面拖拽 YAML 可以正常导入。拖拽后客户端会生成内部副本，修改原始 YAML 不会自动更新已导入配置。
- TUN 和系统代理可以使用同一套 YAML 规则，但负责接管流量的入口不同。TUN 已开启时通常不必再开系统代理。
- 最终决定是不搭建订阅服务、不依赖 sslip.io 或额外域名，继续维护本地 YAML。

<a id="traffic-flow-permissions"></a>
### 2.3 访问流程与权限边界

访问路径是：

~~~text
应用程序
  -> Clash Verge / Mihomo
  -> 按 YAML 规则选择 DIRECT 或 PROXY
  -> PROXY 时通过 VLESS + REALITY 加密连接日本服务器 TCP 443
  -> Xray 从日本服务器访问目标网站
  -> 响应沿原路返回
~~~

持有 YAML 的人可以使用该 UUID 经过服务器出网、消耗带宽，并让目标网站看到服务器出口 IP。YAML 不能直接提供 Linux 登录、root、SSH、VNC、服务器文件读写或 Xray 管理权限。

<a id="xray-vless-reality-components"></a>
## 3. Xray、VLESS 与 REALITY 组件

<a id="component-functions"></a>
### 3.1 各组件的功能

| 名称 | 功能 |
|---|---|
| Xray | 服务器上的网络代理程序，监听端口、校验用户并转发流量 |
| VLESS | Xray 使用的轻量用户认证和数据传输协议 |
| REALITY | 为 VLESS 连接提供类似正常 TLS 的加密和握手伪装 |
| TCP 443 | Xray 对外监听的网络入口；443 是常见 HTTPS 端口 |
| UFW | Ubuntu 防火墙管理工具，决定哪些端口和流量允许进入或转发 |
| UUID | VLESS 用户身份标识，用于允许或撤销某位用户 |
| PrivateKey | REALITY 服务器私钥，只能留在服务器端，不能发给客户端 |
| PublicKey | 由私钥对应产生的公开参数，客户端连接时使用 |
| short-id | REALITY 握手匹配参数之一，可随客户端配置分发 |
| SNI / serverName | 客户端握手时使用的目标域名，本节点为 www.iij.ad.jp |

<a id="uuid-keys-port-sharing"></a>
### 3.2 UUID、密钥与端口共享

同一个 IP:端口通常只能由一个监听进程占用，但一个 Xray 入站可以在 TCP 443 上配置多个客户端 UUID。因此“服务监听一个端口”和“每位用户一个端口”不是同一件事：

- Xray 进程统一占用 TCP 443。
- 多位用户共享相同 IP、端口和 REALITY 公共参数。
- Xray 根据 UUID 区分用户。
- 删除某个 UUID 即可只撤销该用户，不影响其他 UUID。
- 只有需要完全不同的协议、独立统计、独立入口策略或隔离故障时，才考虑额外端口或额外入站。

<a id="shadowrocket-vs-clash-verge"></a>
### 3.3 小火箭与 Clash Verge 的区别

小火箭和 Clash Verge 都可以作为 VLESS 客户端；协议相同，差异主要在客户端平台、配置形式和分流能力。

| 比较维度 | 小火箭 Shadowrocket | Clash Verge / Mihomo |
|---|---|---|
| 常见平台 | iPhone / iPad | Windows、macOS、Linux |
| 常见导入 | vless:// 链接、订阅 | YAML、订阅 |
| 分流规则 | 使用小火箭自己的规则体系 | 使用 Mihomo YAML rules、rule-providers |
| 系统接管 | iOS VPN 扩展 | 系统代理或 TUN 虚拟网卡 |
| 节点本质 | 都是使用同一组 VLESS + REALITY 连接参数 | 都是使用同一组 VLESS + REALITY 连接参数 |

<a id="user-isolation-expiry"></a>
## 4. 用户隔离与到期管理

<a id="one-user-one-uuid-yaml"></a>
### 4.1 一位用户一个 UUID 和 YAML

技术上可以多人共用同一个 UUID 和 YAML，但不推荐。独立 UUID 有三项直接收益：

1. 单独撤销，不影响其他人。
2. 可以把异常或流量归属到具体用户。
3. 可以为某位用户设置独立到期时间。

因此当前约定是“一位用户一个 UUID、一份本地 YAML”。三份 YAML 的代理地址和规则可以相同，UUID 必须不同。

<a id="three-user-status"></a>
### 4.2 三位用户的当前状态

| 用户 | 服务端身份标记 | 本地配置 | 到期策略 |
|---|---|---|---|
| 用户 1 | 独立 UUID | japan_xray_reality.yaml | 未设置自动到期 |
| 用户 2 | user2-20260803，独立 UUID | japan_xray_reality_user2.yaml | 自动到期已取消 |
| 用户 3 | user3-20260803，独立 UUID | japan_xray_reality_user3.yaml | 未设置自动到期 |

知识库不保存三位用户的 UUID 明文。需要恢复或轮换时，以服务器 Xray 配置和各自 YAML 为准，并按敏感凭证管理。

<a id="user2-expiry"></a>
### 4.3 用户 2 的到期设置（已取消）

用户 2 曾配置自动到期，原定时间为：

- UTC：2026-08-18 03:46:19
- 日本时间：2026-08-18 12:46:19
- 中国时间：2026-08-18 11:46:19

原设计使用 xray-expire-user2.timer 触发 /usr/local/sbin/xray-expire-user2：备份 Xray 配置、移除用户 2、验证候选配置、重启 Xray，并在失败时回滚。

该机制已经取消。执行 systemctl disable --now xray-expire-user2.timer 后，截至 2026-08-10 的实际验证结果为：

- 定时器：disabled 且 inactive。
- Xray：active，TCP 443 正常监听，配置校验通过。
- 用户 2：服务端条目仍存在，UUID 与本地 japan_xray_reality_user2.yaml 一致。
- 用户 2 的本地 YAML 没有被删除，也不会在原定时间自动失效。

若以后要恢复到期机制，需要重新启用定时器或重新设定一套明确的到期流程；不要仅假定旧定时器仍在运行。

<a id="clash-local-import"></a>
## 5. Clash Verge 本地导入与维护

<a id="drag-drop-import"></a>
### 5.1 正确导入方式

当前实测可用的方法是：把 YAML 文件直接拖到 Clash Verge 的“订阅/配置”页面，然后激活导入的配置。不同版本界面名称可能变化，不必强行寻找旧教程中的“新建”或“导入本地配置”按钮。

<a id="source-yaml-internal-copy"></a>
### 5.2 原始 YAML 与内部副本

拖拽导入后，Clash Verge 会在 profiles 目录创建随机文件名的内部副本，并由 profiles.yaml 管理配置列表。这会产生两个文件概念：

- **原始 YAML：** 项目 output 目录中的可维护源文件。
- **内部副本：** Clash Verge 当前实际加载的随机文件名 YAML。

修改原始 YAML 后，已导入的内部副本不会自动同步。因此用户 1 曾出现“原始 YAML 已增加国内规则，但当前配置仍只有 MATCH,PROXY”的现象。解决方式是重新拖入更新后的 YAML 并激活，或者谨慎修改客户端内部副本；推荐保留原始 YAML 为唯一维护源，再重新导入。

<a id="edit-routing-rules"></a>
### 5.3 增加或修改规则

本地模式下，可以直接编辑 YAML 的 rules 部分，但需要遵守：

1. 新规则放在 MATCH 之前。
2. 规则从上到下匹配，第一条命中后停止。
3. 修改用户 1 的 YAML 不会自动影响用户 2 和用户 3。
4. 三位用户要保持相同规则时，需要分别更新三份源 YAML。
5. 修改后重新拖入 Clash Verge，并确认当前激活的是新副本。
6. 规则修改只影响客户端分流，不需要修改服务器 Xray。

<a id="domestic-direct-overseas-proxy"></a>
## 6. 国内直连与国外代理规则

<a id="rule-evaluation-order"></a>
### 6.1 规则执行顺序

Mihomo 按 rules 从上到下判断：

- DIRECT：直接使用本机网络和国内出口。
- PROXY：交给 Japan-Xray-Reality，从日本服务器出网。
- REJECT：阻止连接。
- MATCH：兜底匹配所有剩余流量，必须放在最后。

国内规则应在 MATCH,PROXY 之前，否则 MATCH 会提前接管全部流量。

<a id="no-resolve-meaning"></a>
### 6.2 no-resolve 的含义

no-resolve 只作用于相应的 IP 或 GEOIP 规则，表示“不要为了判断这条规则而额外发起 DNS 解析”。它不关闭全局 DNS，也不代表域名永远不解析。

当前原则：

- 局域网和保留地址 CIDR 规则可使用 no-resolve，避免无意义 DNS。
- 最后的 GEOIP,CN,DIRECT 不使用 no-resolve，让未列出的域名在解析到中国 IP 后仍能直连。
- 一个域名已被 DOMAIN 或 DOMAIN-SUFFIX 命中时，不会继续向下检查 GEOIP。

<a id="current-rule-strategy"></a>
### 6.3 当前规则策略

三份 YAML 的规则保持一致，共 111 条：110 条明确规则加最后一条 MATCH,PROXY。总体逻辑为：

1. localhost、127.0.0.0/8 和常见私有网段直连。
2. .cn 域名及百度、淘宝、天猫、京东、QQ、哔哩哔哩、微信、微博、小红书等常见国内域名直连。
3. 中国 GEOIP 直连，覆盖未手工列出的国内公网服务。
4. 其余流量走日本代理。

该规则参考 NiceDuck 商用订阅的本地规则结构，但将其策略组名称改写为当前自建配置可用的 DIRECT 和 PROXY。

<a id="system-proxy-vs-tun"></a>
## 7. 系统代理与虚拟网卡 TUN

<a id="ingress-differences"></a>
### 7.1 两种入口的差异

系统代理和 TUN 进入 Mihomo 后可以使用同一套分流规则，但接管范围不同：

| 比较维度 | 系统代理 | TUN 虚拟网卡 |
|---|---|---|
| 接管方式 | Windows 把代理地址交给应用 | 创建虚拟网卡并接管路由 |
| 覆盖范围 | 主要是遵守系统代理的浏览器和应用 | 几乎所有 TCP/UDP 应用 |
| 常见遗漏 | 不遵守系统代理的软件会绕过 | 覆盖更完整 |
| 开销 | 较低 | 需要额外路由、DNS 和网络栈处理 |
| 当前用途 | 浏览器等常规应用 | 游戏、命令行、下载器及不遵守系统代理的软件 |

对话中检查到的状态为：TUN 已开启、系统代理关闭、tun.stack 为 gvisor、auto-route 为 true、启用 DNS 劫持、MTU 为 1500。

<a id="recommended-switches"></a>
### 7.2 推荐开关组合

- 只让浏览器和常规应用分流：TUN 关闭，系统代理开启。
- 希望大多数程序和 UDP 都被接管：TUN 开启，系统代理通常关闭。
- TUN 已开启时再开系统代理通常没有必要，可能增加排查复杂度。
- 下载速度或兼容性异常时，可测试 Mihomo mixed 栈；没有问题时不需要为了“更快”盲目改规则。
- TUN 只保证流量进入代理引擎，不保证代理链路一定比直连更快。

<a id="historical-troubleshooting"></a>
## 8. 历史访问与速度排查

<a id="oalur-routing"></a>
### 8.1 oalur.com 为什么走国内流量

访问 https://vip.oalur.com/home?site=US 时，site=US 只是网页查询参数，不参与 Clash 规则匹配。历史解析结果为中国电信地址 113.96.128.28–35，因此未命中显式域名规则后，由 GEOIP,CN,DIRECT 判定为国内直连。

网页中的图片、脚本或接口如果来自其他域名，会分别匹配规则，不保证与主页面使用同一路径。若要强制整个 oalur.com 直连，可在 MATCH 前加入：

~~~yaml
- DOMAIN-SUFFIX,oalur.com,DIRECT
~~~

<a id="chatgpt-youtube"></a>
### 8.2 YouTube 能开但 ChatGPT 进不去

历史排查确认 YouTube 和 ChatGPT 都由 MATCH,PROXY 通过日本节点访问。Cloudflare trace 显示出口 IP 为 64.83.41.3、地区 JP、机房 NRT；YouTube 返回正常响应。

ChatGPT 的测试表现为：默认 curl User-Agent 返回 403，而模拟 Chrome User-Agent 返回 200。这更像浏览器 Cookie、Cloudflare 挑战、扩展拦截或会话状态问题，而不是规则漏配或节点不通。

推荐顺序：

1. 清理 chatgpt.com、openai.com、auth.openai.com 的站点数据。
2. 使用无痕窗口测试。
3. 临时禁用广告拦截、隐私保护或脚本扩展。
4. 确认 Clash 日志中 ChatGPT 域名仍走 PROXY。
5. 再检查 OpenAI 服务状态和出口 IP 信誉。

<a id="github-msi-slow"></a>
### 8.3 GitHub MSI 下载慢

历史日志证明 github.com 和 release-assets.githubusercontent.com 已命中 MATCH 并使用 Japan-Xray-Reality。TUN 当时已开启、系统代理关闭，因此“下载器没有进入规则”不是主要原因。

结论：

- TUN 能接管流量，但不会自动提高速度。
- 增加显式 GitHub PROXY 规则不会改变当前路径，因为它已经走 PROXY。
- 速度瓶颈更可能是本机到日本节点、节点到 GitHub Release CDN、单连接拥塞或 gvisor 栈开销。
- 可对比“系统代理开启、TUN 关闭”的浏览器下载，或测试 mixed 栈。
- 若要长期比较直连和代理，可为 GitHub 建一个可选择 DIRECT/PROXY 的单独策略组，而不是反复改 MATCH。

<a id="subscription-domain-decision"></a>
## 9. 订阅、域名与最终决策

<a id="commercial-subscription"></a>
### 9.1 商用节点为什么不给单独 YAML

商用服务常给订阅 URL，而不是逐个发送 YAML。Clash Verge 通过订阅 URL 下载服务商生成的 YAML，里面可以同时包含节点、规则、流量用量和到期时间。订阅 URL 本身相当于凭证，泄露后他人可能下载并使用节点。

NiceDuck 的本地订阅副本中已经包含国内直连规则和最后的漏网流量策略。这说明“客户端显示规则模式”不代表客户端会自动生成完整规则；实际规则仍来自订阅下发的 YAML 或客户端覆写配置。

<a id="domain-sslip"></a>
### 9.2 域名和 sslip.io 的边界

域名是把易记名称映射到服务器 IP 的 DNS 名称，不一定代表存在一个普通网站。为订阅地址使用域名，主要是为了 HTTPS 证书、迁移 IP 和统一入口。

sslip.io 可以按 IP 自动解析域名，减少购买和配置域名的步骤，但会依赖第三方 DNS 服务。其风险包括第三方不可用、解析策略变化和控制权不完全属于自己。对当前只有三位用户、主要使用本地 YAML 的场景，增加订阅域名、HTTPS 和自动更新机制会提高维护复杂度。

<a id="current-maintenance-decision"></a>
### 9.3 当前维护决策

曾讨论“用户订阅 + 共享规则集”，但最终明确放弃订阅方案，继续使用本地 YAML。当前维护方式是：

1. 服务器统一维护 Xray 入站和各用户 UUID。
2. Windows 项目目录分别保存三位用户 YAML。
3. 需要新增规则时同时更新三份源 YAML。
4. 用户重新拖入更新后的 YAML。
5. 不依赖 sslip.io、额外域名、Caddy 或远程 rule-provider。

<a id="security-boundaries"></a>
## 10. 安全边界与操作注意事项

- 不在知识库记录 root 密码、UUID 明文、REALITY 私钥、订阅 URL、短期令牌或完整客户端链接。
- 服务器 IP、REALITY 公钥、short-id 和 SNI 虽不等于 root 权限，但仍应只发给需要使用节点的人。
- 每位用户使用独立 UUID；人员变更时只删除或轮换该用户 UUID。
- REALITY PrivateKey 泄露时必须更换密钥对并更新所有客户端公钥。
- root 密码曾在对话中出现，应视为已暴露并尽快轮换；当前已为日本服务器启用 SSH 公钥认证，本机 codex_ed25519 可以无密码维护。确认公钥登录稳定后，可再评估关闭 root 密码登录。
- 从互联网下载并直接执行 shell 脚本有供应链风险。类似 curl ... && bash ... 的命令应先单独下载、检查脚本内容和来源，再执行；脚本末尾删除自身不会消除安装后的程序和配置。
- UFW 检查时处于 inactive。若启用防火墙，至少要先保证 SSH 22 和 Xray TCP 443 的规则正确，避免锁死远程管理。
- 客户端 YAML 的泄露风险主要是代理滥用、带宽消耗和出口责任归属，不是自动获得服务器管理权限。

<a id="maintenance-verification"></a>
## 11. 维护与验证清单

修改 Xray 用户或 REALITY 配置后：

1. 备份 /usr/local/etc/xray/config.json。
2. 使用当前 Xray 二进制验证候选配置。
3. 重启 xray.service。
4. 确认服务为 active。
5. 确认 TCP 443 正常监听。
6. 分别使用仍有效的用户测试连接。
7. 当前约定是用户 2 不自动到期，确认 xray-expire-user2.timer 保持 disabled 且 inactive。

修改 Clash YAML 后：

1. 确认 YAML 语法有效。
2. 确认 MATCH,PROXY 是最后一条。
3. 确认三份用户配置是否需要同步规则。
4. 重新拖入 Clash Verge 并激活新副本。
5. 通过日志验证国内域名走 DIRECT、国外域名走 PROXY。
6. 不要只看“规则模式”按钮，应查看具体规则命中和策略组。
