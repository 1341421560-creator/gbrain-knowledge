<a id="what-is-gbrain"></a>
## 1. GBrain 是什么

GBrain 是一个面向 AI Agent 的个人知识库系统。它把可读、可备份的 Markdown 知识与本地数据库检索结合起来，并通过 MCP 向 Codex 等 AI 工具提供搜索、读取、写入和同步能力。

适合保存的内容包括：

- Amazon 运营经验、广告优化、Listing、物流和账号健康知识。
- 服务器配置、Linux、网络、防火墙和安全事件处理知识。
- 项目决策、操作流程、故障排查记录和长期参考资料。

知识领域可以很杂，不需要为每个领域单独安装一套 GBrain。可以通过目录、标签和页面链接区分领域。

<a id="markdown-and-pglite"></a>
## 2. Markdown 与 PGLite 的区别

<a id="markdown-source"></a>
### Markdown 知识库

Markdown 是原始知识和长期资产，适合人工阅读、编辑、备份和使用 Git 管理。

本机位置：

```text
C:\software\GBrain\brain
```

<a id="pglite-database"></a>
### PGLite 数据库

PGLite 是 GBrain 的本地数据库和检索层，主要保存页面记录、文本分块、搜索索引、来源信息、同步状态及其他运行数据。它不需要单独安装数据库服务器，也不适合手工编辑。

本机位置：

```text
C:\software\GBrain\.gbrain\brain.pglite
```

工作关系：

```text
编辑 Markdown → GBrain 同步 → PGLite 建立索引 → Codex/MCP 查询
```

> **结论：** 日常编辑 Markdown；完成一轮修改后，让 GBrain 更新 PGLite。

> **警告：** 不要把 PGLite 当作文档编辑器，也不要在没有备份和明确操作步骤的情况下直接删除数据库目录。

<a id="markdown-format"></a>
## 3. Markdown 格式、命名与索引优化

<a id="markdown-frontmatter"></a>
### Markdown 是固定格式吗

GBrain 可以读取普通 Markdown，也能在导入时推断部分缺失信息，但为了通过检查并方便长期维护，推荐至少保留以下字段：

```markdown
---
title: 页面标题
type: note
tags: [主题一, 主题二]
created: "2026-07-25"
---

# 页面标题

## 主题

正文内容。
```

其中 `title`、`type` 和 `created` 是推荐的基础字段；`tags`、`aliases`、`updated`、`subtype` 和 `Timeline` 按需使用。

<a id="indexing-guidelines"></a>
### 怎样方便 PGLite 索引

- 一篇文件集中讲一个主题。
- 标题和小标题直接包含实际关键词。
- 使用 `##` 和 `###` 划分语义明确的章节。
- 避免超长段落，将不同观点拆成独立段落或列表。
- 标签保持少而准确，通常使用 3～8 个。
- 内容特别长时拆成多篇，并用 Markdown 链接或 GBrain 页面链接关联。
- 重要概念应自然出现在正文中，不要只写在标签里。

GBrain 会优先按段落、换行、句号和中文标点进行分块，目标约为每块 300 个词或中文字符单位，并保留一定重叠。清晰的语义结构比特殊排版更重要。

<a id="chinese-filenames"></a>
### Markdown 文件名可以使用中文吗

可以。当前版本会保留汉字作为页面 slug，例如：

```text
Amazon广告优化.md
服务器防火墙排查.md
GBrain常见问题.md
```

建议避免 Windows 禁止字符、emoji、过长名称和大量特殊符号。页面被其他知识链接后，不要频繁改名，否则对应 slug 和链接也可能需要更新。

如果更重视跨平台兼容性，可以采用稳定英文文件名和中文标题：

```text
文件名：gbrain-faq.md
标题：GBrain 常见问题
```

<a id="blank-lines"></a>
### 可以删除空白行吗

可以删除多余的连续空白行，但不要删除所有块间空行。建议在标题、正文、列表和代码块之间保留一个空白行。

```markdown
# 标题

正文段落。

## 小标题

- 列表一
- 列表二
```

三个以上的连续换行可以压缩成一个空白行。完全删除段落间隔可能导致正文合并、列表或代码块渲染异常，也会减少可用于分块的段落边界。

<a id="codex-mcp"></a>
## 5. Codex 如何连接 GBrain

<a id="stdio-mcp"></a>
### STDIO MCP 是什么

STDIO MCP 使用标准输入和标准输出传递 MCP 请求。Codex 启动时会创建一个 `gbrain serve` 子进程，并通过该子进程的 stdin/stdout 调用 GBrain 工具。它不需要监听端口，适合只有一个本地客户端的简单场景。

STDIO 的进程生命周期通常跟随客户端。多个独立的 Codex、CLI 或 IDE 客户端可能分别启动自己的 `gbrain serve`，每个进程都会尝试打开同一个 PGLite 数据目录。

<a id="http-mcp"></a>
### HTTP MCP 是什么

HTTP MCP 将 GBrain 作为一个独立、长期运行的服务。Codex 不再为每个客户端创建 GBrain 子进程，而是通过 HTTP 连接固定的 MCP 地址。

HTTP MCP 既可以部署到远程服务器，也可以像本机当前配置一样只监听 `127.0.0.1`。只监听回环地址时，它仍然是本地服务，不会自动暴露到局域网或互联网。

<a id="singleton-http-mcp"></a>
### 单例 HTTP MCP 是什么

“单例”不是新的 MCP 协议，而是一种运行架构：本机只保留一个 GBrain HTTP 服务进程，所有 Codex 任务共享这个服务，由该进程统一持有 PGLite。

```text
Codex 任务 A ─┐
Codex 任务 B ─┼→ 单例 GBrain HTTP MCP → PGLite
Codex 任务 C ─┘
```

<a id="current-http-architecture"></a>
### 当前架构：Windows 常驻 HTTP MCP

2026-07-25 已从 STDIO MCP 切换为单例 HTTP MCP：

```text
多个 Codex 任务
      │
      ├───────────────┐
      ▼               ▼
http://127.0.0.1:3131/mcp
      │
GBrain HTTP 常驻进程（唯一）
      │
PGLite（唯一持有者）
```

Codex 全局配置位于：

```text
C:\Users\AI454\.codex\config.toml
```

当前配置：

```toml
[mcp_servers.gbrain]
url = "http://127.0.0.1:3131/mcp"
bearer_token_env_var = "GBRAIN_REMOTE_TOKEN"
```

服务只绑定 `127.0.0.1:3131`，不会接受局域网或公网连接。OAuth 客户端具有 `read write admin` 权限，写入来源和联合读取范围均绑定到 `personal`。令牌有效期设置为 `315360000` 秒；可以提前轮换，不在知识库保存令牌原文。

Codex 配置或用户环境变量修改后，应完全退出并重新打开 Codex，让新的 `app-server` 重新读取配置和令牌。

<a id="windows-autostart"></a>
### Windows 自动启动与手动启动

Windows 任务计划程序中已注册：

```text
任务名称：GBrain HTTP MCP
触发方式：当前用户登录时
端口：3131
绑定地址：127.0.0.1
失败重试：最多 3 次，每次间隔 1 分钟
重复实例：忽略新实例
```

手动启动方法：

```powershell
Start-ScheduledTask -TaskName "GBrain HTTP MCP"
```

也可以按 `Win + R`，输入 `taskschd.msc`，在“任务计划程序库”中找到 `GBrain HTTP MCP`，右键选择“运行”。不要直接双击 `bun.exe`，也不要重复手工执行 `gbrain serve`。

健康检查：

```text
http://127.0.0.1:3131/health
```

2026-07-27 核验结果：HTTP 状态码为 `200`，GBrain 版本为 `0.42.65.0`，数据库引擎为 `pglite`。

当前任务直接运行 Bun，因此登录后会显示 GBrain 控制台窗口。这个窗口就是 HTTP 服务进程：不需要为每个 Codex 任务分别启动，但窗口关闭后服务也会停止。以后可以将计划任务改为后台隐藏运行；隐藏后任务管理器中仍会保留一个 `bun.exe`。

<a id="why-singleton-http"></a>
### 为什么从 STDIO 切换到单例 HTTP

旧的 STDIO 架构由 Codex 为 MCP 启动一个子进程。即使多个任务处于同一个 `codex app-server` 下，也出现过其他任务无法可靠复用 STDIO 会话的问题；多个独立 Codex/CLI/IDE 进程还可能分别启动 GBrain，争抢同一 PGLite 锁。

PGLite 是嵌入式数据库，同一个数据库目录不能被多个独立进程同时打开。HTTP 架构让所有客户端连接一个常驻 GBrain，由唯一进程持有 PGLite，从架构上避免多进程抢锁。

<a id="singleton-http-limits"></a>
### 单例 HTTP MCP 没有解决什么

单例 HTTP 解决的是“多个 MCP 服务进程争抢 PGLite”，但不会让 PGLite 变成支持任意多进程并发的服务器数据库。HTTP 服务运行时，另一个直接执行 `gbrain search`、`gbrain get` 或 `gbrain sync` 的 CLI 进程仍可能因数据库锁而失败。

因此：

- 日常搜索、读取和写入优先通过 HTTP MCP 完成。
- 不要在 HTTP 服务运行时再启动 STDIO GBrain。
- 大规模本地 CLI 同步前，应受控停止 HTTP 服务，同步完成后再恢复。
- 如果长期需要多个独立进程直接访问数据库，应考虑迁移到 PostgreSQL。
- MCP 配置发生变化后，旧 Codex 任务可能仍保留旧的工具握手结果；应重启 Codex或创建新任务重新连接。

<a id="concurrency"></a>
### 并发能力

HTTP MCP 是无状态请求，没有固定的 Codex 任务数量上限。2026-07-25 本机实测：20 路同时调用 `get_page`，20 次全部成功，失败 0 次，总耗时约 320ms。

当前建议：

- 搜索和读取：可同时运行约 10～20 个 Codex 任务。
- 创建和修改页面：建议同时不超过 3～5 个任务。
- 修改同一页面、批量同步或其他重写操作：尽量串行。
- 50 个以上长期并发或大量写入：考虑把数据库后端改为 PostgreSQL。

任务数不等于请求数，一个任务可能连续调用多个 MCP 工具。PGLite 仍是单写入引擎，并发写入会在同一进程内排队。

<a id="prompt-examples"></a>
### 常用提示词

```text
使用 GBrain 搜索我以前记录的 Amazon 广告知识。
```


<a id="query-timing"></a>
## 6. 什么时候查询 GBrain

适合查询的情况：

- 问题涉及以前保存的个人经验、规则或决策。
- 需要复用历史故障处理方法。
- 需要确认个人流程，而不是获取通用互联网知识。
- 新信息可能与已有知识重复或矛盾。
- 回答前需要找到具体的原始笔记。

不一定需要查询的情况：

- 简单计算、翻译或与个人知识无关的常识问题。
- 明确要求查询最新互联网信息的问题。
- 当前对话已经包含完整信息，而且不需要历史背景。

<a id="usage-cost"></a>
## 7. 使用成本与消耗

- GBrain、MCP 协议和本地 PGLite 查询本身不单独收费。
- 关键词搜索主要在本机运行，不需要为数据库查询支付费用。
- Codex 读取检索结果后，这些内容会占用当前模型的上下文和 token。
- 返回内容越多、对话越长，模型消耗通常越高。
- 当前已启用 Ollama 本地 Embedding：`qwen3-embedding:8b`，向量生成与查询没有远程 API 调用费。
- 本地 Embedding 会使用本机 GPU、电力和硬盘；Codex 读取检索结果并生成答案时，仍会消耗 Codex/ChatGPT 对应套餐或 API 用量。
- 使用需要模型参与的查询扩展、总结或其他 AI 功能时，可能调用已配置的模型服务并产生对应费用。

为了控制消耗，查询时应尽量说明主题、范围和期望返回的结果数量。

<a id="organize-knowledge"></a>
## 8. 如何整理杂乱知识

<a id="knowledge-placement"></a>
### 知识应该放在现有章节、文件还是新文件夹

更新知识库时，应先判断新知识与现有结构的关系，再决定放置层级。目标是既避免把所有内容堆进一个文件，也避免把紧密相关的内容拆得过碎。

判断顺序：

1. **放进现有章节：** 新知识与某个现有小标题直接相关，并且使用场景、主题和维护周期一致时，补充到该章节，不新增目录项。
2. **在现有文件中新增章节：** 新知识属于同一文件的核心主题，但无法自然放进现有章节时，新增 `##` 或 `###`，并同步更新目录和稳定锚点。
3. **新建 Markdown 文件：** 新知识具有独立主题、篇幅较长、检索关键词明显不同，或者需要单独维护和引用时，新建文件，并从相关页面建立链接。
4. **新建文件夹：** 一个新知识领域预计会包含多篇文件，或者已经形成稳定的子领域、职责和维护边界时，新建文件夹；只有一篇孤立文档时通常不需要单独建文件夹。
5. **拆分过大的现有文件：** 当一个文件包含多个独立主题、搜索结果相互干扰或完整读取上下文过大时，按主题拆分，并保留一篇总览页面负责导航。

每次新增或移动知识后，都要检查：

- 文档目录是否覆盖新增章节。
- 标题和锚点是否仍然有效。
- 相关页面是否需要增加双向链接。
- 文件名、slug、标签和目录位置是否仍符合主题。
- PGLite 是否已经更新并能够检索到新内容。

> **原则：** 先复用合适的现有结构；现有结构不再适合时，再逐级新增章节、文件或文件夹。

<a id="knowledge-structure-owner"></a>
### 由谁判断和创建知识结构

知识归档位置由 Codex 判断，GBrain 不会自主决定新知识应该进入哪个章节、Markdown 文件或文件夹。

职责分工：

- **Codex：** 理解知识语义，检索现有页面和章节，决定复用现有章节、新增章节、新建文件或新建文件夹；同时维护页面目录、稳定锚点和相关链接。
- **GBrain：** 按照 Codex 指定的 slug 和路径写入 Markdown，更新页面、分块、PGLite 索引和 Embedding。
- **Ollama：** 为新增或变化的知识块生成向量，不负责分类或决定目录。
- **PGLite：** 保存页面、分块、关键词索引和向量索引，不负责设计知识结构。

执行流程：

```text
用户提供知识
→ Codex 搜索现有页面、章节和目录
→ Codex 判断放置层级
→ Codex 调用 GBrain 写入
→ GBrain 更新 Markdown、PGLite 和 Embedding
```

建议把简短的强制归档顺序写入 `AGENTS.md`，让每个 Codex 任务在创建知识前都能直接遵守；本页保留详细判断标准和维护说明。实际文件名应为 `AGENTS.md`，不是 `agent.md`。


不必先把全部知识整理完成再使用。推荐采用“先收集、后整理”的方式：

1. 新内容先放入 `inbox`。
2. 让 Codex 判断所属领域并整理标题、标签和结构。
3. 不确定的内容继续保留在 `inbox`，不要强行分类。
4. 定期检查重复页面、孤立页面和过期内容。
5. 整理完成后运行同步，让 PGLite 更新索引。

建议逐步形成以下目录：

```text
brain\
├─ inbox\
├─ amazon\
│  ├─ listing\
│  ├─ advertising\
│  ├─ logistics\
│  └─ account-health\
├─ server-security\
│  ├─ linux\
│  ├─ firewall\
│  ├─ network\
│  └─ incident-response\
└─ gbrain\
```

推荐分工：

- 用户负责输入内容和最终确认。
- Codex 负责格式化、分类、命名、摘要和建立关联。
- GBrain 负责存储、索引、搜索和通过 MCP 提供工具。

<a id="sync-pglite"></a>
## 9. 修改 Markdown 后如何更新 PGLite

Markdown 与 PGLite 是两层存储。手动修改 Markdown 后，PGLite 不会立即自动感知，完成一轮有意义的修改后需要同步。

<a id="mcp-write"></a>
### 通过 GBrain HTTP MCP 写入

让 Codex 使用 `put_page` 等 GBrain MCP 工具保存或更新页面时，PGLite 会在写入过程中更新，通常可以立即搜索，不需要再运行同步。

推荐提示词：

```text
把这段内容整理后保存到 GBrain，并更新索引。
```

<a id="manual-markdown-sync"></a>
### 手动编辑 Markdown

当前个人知识库是 Git 来源。手工修改 Markdown 后，推荐通过正在运行的 HTTP MCP 服务提交后台同步任务，而不是启动第二个会直接打开 PGLite 的 CLI 进程。

推荐流程：

~~~text
保存并检查 Markdown
→ 按当前 Git 来源要求提交变更
→ 通过 MCP submit_job 提交 sync 任务
→ 使用 get_job 或 get_job_progress 等待任务完成
→ 检查页面、chunk 和健康状态
→ missing_embeddings 大于 0 时再提交 embed 任务
~~~

后台 `sync` 任务在常驻 GBrain 服务内部执行，复用同一个数据库引擎，因此不需要为了该任务停止 HTTP MCP。同步任务和写入任务应按 source 串行处理，避免同时改写同一来源或同一页面。

如果必须直接运行独立的 `gbrain sync`、`gbrain embed` 等本地 CLI 命令，另一个进程会尝试打开同一个 PGLite。此时才需要受控停止 `GBrain HTTP MCP`，完成 CLI 操作后立即恢复服务。

> **结论：** MCP 后台任务优先；独立 CLI 是需要释放 PGLite 锁的例外路径。

<a id="embedding-query-flow"></a>
### HTTP MCP、GBrain、Ollama 与 PGLite 的关系

四者属于不同层，不互相替代：

- **HTTP MCP：** Codex 与 GBrain 之间的访问通道。
- **GBrain：** 协调知识写入、分块、向量生成和检索。
- **Ollama：** 把知识块或问题转换成固定维度的语义向量。
- **PGLite：** 保存 Markdown 的索引副本、文本分块、关键词索引和向量索引。

建立索引：

```text
Markdown
→ GBrain 分块
→ Ollama 生成内容向量
→ GBrain 把内容和向量写入 PGLite
```

日常查询：

```text
Codex
→ HTTP MCP
→ GBrain
→ Ollama 把问题生成查询向量
→ PGLite 混合检索关键词与向量
→ GBrain 通过 HTTP MCP 返回相关片段
→ Codex 组织最终答案
```

HTTP MCP 不是索引，也不会因为保持运行而破坏 Embedding。日常应保持 GBrain HTTP MCP 运行，否则 Codex 无法访问知识库。只有运行需要独占 PGLite 的本地 CLI 同步、回填、重建或迁移操作时，才临时停止 HTTP MCP，完成后立即恢复。

Ollama 也需要在语义查询时可用，因为每个新问题都要生成查询向量。关闭 Ollama 不会删除 PGLite 中已有向量，但语义检索可能失败或降级为关键词路径。

<a id="embedding-update"></a>
### 新增和更新知识时怎样维护向量

日常新建或更新知识时，不修改 Ollama 的向量维度。当前整个知识库统一使用 1280 维：

- **向量维度：** 相当于统一的数据格式，设置一次后保持不变。
- **内容向量：** 每个知识块的语义索引；新增或修改知识时，只为变化的知识块生成新向量。
- **向量存放位置：** PGLite。Ollama只负责生成，不保存知识库索引。

通过 GBrain MCP 的 `put_page` 更新页面时，GBrain 会更新 Markdown、页面记录、分块和对应向量。手动修改或批量同步后，应检查 `missing_embeddings`；大于 0 时，在受控停止 HTTP MCP 后运行 `gbrain embed --stale`。

`--stale` 只处理新增或变化的知识块，不需要每次重做整个知识库。只有更换 Embedding 模型或改变维度时，才需要全库重新生成向量；如果新维度与 PGLite 列宽不同，还需要使用受支持的重建或迁移流程。


<a id="embedding-maintenance"></a>
### 日常维护

通过 GBrain MCP 的 `put_page` 更新页面时，会在同一次写入流程中更新页面记录、Markdown 写回、分块和对应向量。手动编辑或批量同步后，应检查健康状态中的 `embed_coverage` 与 `missing_embeddings`。

优先维护流程：

~~~text

→ 等待同步任务完成
→ 检查 get_health
→ missing_embeddings > 0 时 submit_job(embed)
→ 等待回填完成
→ 再次检查健康状态和自然语言检索
~~~

只有必须直接运行本地 CLI 时，才按以下顺序释放 PGLite：

~~~powershell

Start-ScheduledTask -TaskName "GBrain HTTP MCP"
~~~

完成后检查：

- HTTP 健康端点返回 `status: ok`。
- `embed_coverage` 为 `1`，表示 100%。
- `missing_embeddings` 为 `0`。
- 自然语言搜索能够返回高相关 chunk。

> **警告：** 不要为了切换模型随意删除 PGLite，也不要在 HTTP 服务持有数据库时运行第二个直接访问 PGLite 的 GBrain CLI 进程。

<a id="codex-retrieval-policy"></a>
## 12. Codex 检索与上下文访问策略

<a id="retrieval-responsibilities"></a>
### GBrain 原生检索与 Codex 策略的职责

GBrain 原生已经提供按 chunk 检索的 `search` 接口。Chunk-only 不是重新实现一套向量检索，而是规定 Codex 应如何使用现有接口，以及哪些工具结果可以进入模型上下文。

职责边界：

- **GBrain `search`：** 在已经建立的 chunk 索引中查询并返回候选片段，结果通常包含 `slug`、`chunk_id`、`chunk_index`、`chunk_text`、相关性分数和证据类型。
- **GBrain `get_chunks`：** 返回某个页面的全部 chunk，适合检查切分或在已知页面内补充片段，不是普通问答的默认入口。
- **GBrain `get_page`：** 返回完整逻辑页面，包含完整正文和页面元数据，适合整页审核、编辑和结构检查。
- **Codex：** 判断是否需要访问个人知识库、构造查询、限制主题范围、过滤候选、决定最终使用哪些 chunk，并组织答案。

GBrain 不会替 Codex 判断一个候选是否获得了进入当前对话上下文的授权；MCP 也只是访问通道。最终上下文由 Codex 的工具调用和输出策略决定。

<a id="gbrain-call-decision"></a>
### 什么时候调用 GBrain

在调用工具前先区分问题类型：

| 问题类型 | 默认处理 |
|---|---|
| 用户明确要求查询、引用或更新知识库 | 调用 GBrain |
| 用户的历史配置、故障、经验、流程、决策或内部约定 | 调用 GBrain |
| 通用且稳定的基础知识 | Codex 直接回答，不为确认是否收录而预搜 GBrain |
| 最新政策、价格、费率、法律、平台规则或软件版本 | 查询互联网或官方来源；用户要求时再对照 GBrain |
| 当前对话已经提供完整材料且不需要历史背景 | 优先使用当前对话 |

“正在执行知识库任务”本身不是扩大检索范围的理由。允许访问的主题由当前问题、用户提供的材料和回答必需的事实关系决定。

<a id="search-query-interface"></a>
### `search(query)` 是什么

`search(query)` 是对 GBrain MCP 搜索接口的概念写法。用户通常不需要手动输入命令，而是由 Codex 代表用户提交查询文本和候选数量。

当前查询链路：

~~~text
用户问题
→ Codex 判断需要访问个人知识库
→ Codex 构造限定主题的 query
→ Ollama 生成查询向量
→ PGLite 进行关键词与向量的混合检索和排序
→ GBrain 返回候选 chunk
~~~

Embedding 表示语义相似度，不表示事实正确、主题授权或最终可用。切分器负责生成 chunk，Ollama 负责把问题和 chunk 转为向量，PGLite 保存并检索这些索引。

<a id="chunk-only-context"></a>
### Chunk-only 上下文流程

普通知识库问答使用以下流程：

~~~text
判断是否调用 GBrain
→ search 返回多个候选 chunk
→ 工具执行环境进行轻量准入过滤
→ 只输出实际采用的少量 chunk_text 与来源 slug
→ Codex 综合回答
~~~

取得 `slug` 后不需要再次读取 Markdown。`search` 结果已经包含候选 `chunk_text`；slug 主要用于来源识别、范围过滤和回答引用。普通问答不得因为取得 slug 就自动调用 `get_page`。

短页面可能只被切成一个 chunk。此时单个命中 chunk 可能看起来接近完整页面，但它仍然来自 `search` 的一个 chunk，不代表调用了 `get_page`。

<a id="candidate-admission-filter"></a>
### 候选 chunk 的轻量准入过滤

搜索结果是候选集合，不是最终上下文。候选应先留在工具执行环境中，完成以下轻量检查：

- 排除与当前问题主题、实体或限定条件明显不一致的 slug 和 chunk。
- 排除弱相关、重复、空内容、错误来源，以及不满足当前问题时效要求的结果。
- 历史问题不得仅因资料时间较早而排除；应判断它是否符合所询问的历史时间。
- 删除与回答无关的原始 JSON 字段，并限制最终输出数量。
- 禁止把未经处理的完整搜索 JSON 直接交给 Codex。

工具内部过滤不是再运行一次完整的语义检索，而是对检索候选做准入控制。未通过过滤、未被工具输出的原始候选不会成为 Codex 的模型上下文；本地检索和 JavaScript 过滤会产生本机计算与工具开销，但不会按候选全文占用模型上下文 token。

<a id="adaptive-candidate-count"></a>
### 候选数量与多轮检索

候选数量按问题复杂度动态确定，而不是固定为 3～5 条：

- 简单定义或单一事实：通常取 5～8 个候选。
- 单一主题但答案可能分散：通常取 8～15 个候选。
- 多主题或跨相关知识领域：拆分子问题，每个子问题通常取 8～15 个候选。
- 特别复杂的子查询：候选上限通常为 20。

候选池可以适当放大以保证召回率，因为它先在工具环境中过滤；真正进入 Codex 上下文的 chunk 应按证据需要控制，通常为 1～10 个，复杂问题可适当增加。不得为了凑数量保留弱相关内容。

首轮信息不足时，先缩小、拆分或改写查询后再次搜索。多轮 chunk 检索仍不足时，应说明知识库证据不足，不得自动读取整页。

<a id="multi-slug-domains"></a>
### 多 slug、多个章节与跨知识领域

一个答案可以使用来自多个 slug、多个章节和多个 chunk 的证据。Chunk-only 限制的是进入上下文的内容单位，不限制只能使用一个页面。

当问题明确包含多个知识主题时，应先拆成子问题，对每个主题分别搜索和过滤，再检查重复、矛盾、版本与时效性后综合回答。跨知识领域必须由问题本身或必要事实关系触发，不能因为搜索结果有弱语义相似就扩展领域。

例如 Amazon 广告与 Listing 转化率的关联问题可以分别检索广告和 Listing；单独询问 ACoS 时，服务器、VPN 或 GBrain 运维页面即使出现在候选中也必须排除。

<a id="full-page-exceptions"></a>
### 完整页面读取例外

`get_page(slug)` 不用于普通知识问答。以下任务需要页面整体结构时可以读取全文：

- 用户明确要求查看、审核、总结或导出整篇页面。
- 编辑、更新、重构、拆分或合并知识库 Markdown。
- 核对完整目录、标题层级、稳定锚点、交叉链接或整体结构。
- 用户明确同意为当前任务读取指定完整页面。

完整页面读取权限只适用于当前任务和已确定页面，不自动延续到后续问题，也不扩展到其他 slug。

<a id="shadowrocket-retrieval-test"></a>
### Shadowrocket 历史配置检索测试

2026-07-27 使用“以前服务器如何配置 Shadowrocket 节点”的个人历史问题测试本策略。该问题明确涉及服务器历史配置，因此允许访问 `服务器与网络/*`。

测试结果：

- 命中页面为 `服务器与网络/节点配置/小火箭转发节点`，证据类型为高向量匹配，状态未过期。
- 未调用 `get_page`，也没有加载其他服务器页面。
- 命中页面较短，全部主要内容位于 `chunk_index 0`，所以单个 chunk 视觉上接近整页。
- 知识库保留了服务端方案、端口、协议和维护边界，但没有保存节点明文密码。

这个测试同时说明：访问 `服务器与网络/*` 不是静态禁止项；当问题本身明确涉及服务器时应正常检索。真正需要防止的是无关问题因弱语义相似而误用服务器候选。

<a id="hidden-dot-directories"></a>
## 13. 知识库中的隐藏点目录

<a id="dot-directory-sync-behavior"></a>
### `.gbrain/` 是否参与默认同步

按当前 GBrain 文件扫描与同步代码，位于知识库根目录下的 `C:\software\GBrain\brain\.gbrain\` 属于以点开头的隐藏目录。标准文件系统扫描和 Git 快速扫描都会对每个路径段应用目录裁剪规则，因此不会进入该目录，也不会把其中的 Markdown 自动同步、切分或生成 Embedding。

这与 GBrain 的运行数据目录 `C:\software\GBrain\.gbrain\` 不是同一个位置：

~~~text
C:\software\GBrain\brain\.gbrain\   知识库内部的隐藏目录，默认不参与文件扫描
C:\software\GBrain\.gbrain\         GBrain 配置和 PGLite 运行数据目录
~~~

<a id="dot-directory-boundaries"></a>
### 隐藏目录的边界与旧索引

点目录是文件扫描排除规则，不是通用权限系统：

- 新放入 `.gbrain/` 的 Markdown 默认不会通过文件同步进入索引。
- 已经存在于 PGLite 的旧页面不会因为创建点目录就自动消失；移动旧文件后需要同步并核验旧 slug。
- 通过绕过文件扫描的直接写入接口仍可能创建数据库页面，因此不应把点目录当成绝对安全边界。
- Codex 的本地文件工具仍可能读取点目录；是否允许读取仍由用户指令和 AGENTS.md 约束。

<a id="gbrain-folder-choice"></a>
### `知识库管理/` 与 `.gbrain/` 的选择

| 目标 | 建议目录 |
|---|---|
| 内容仍要被 GBrain 搜索，但普通问题不得误用 | 保留 `知识库管理/`，使用主题准入和工具过滤 |
| 内容完全不希望出现在常规 GBrain 搜索候选中 | 使用 `.gbrain/`，并确认旧索引已清理 |
| 保存 GBrain 运行配置、数据库和日志 | 使用知识库外部的 `C:\software\GBrain\.gbrain\` |

2026-09-21 按用户要求完成中文分类后，本页位于 `知识库管理/常见问题与本机配置.md`；原 `gbrain/` 分类迁至 `知识库管理/`。该目录仍仅用于 GBrain 自身的安装、配置、索引和维护资料。外部 AGENTS.md 如仍使用旧目录名，应将同样的访问边界对应到 `知识库管理/`；本次没有修改外部规则文件。

<a id="gbrain-folder-access-rule"></a>
### GBrain 专用资料的访问规则

知识库中的 `知识库管理/` 仅用于 GBrain 的安装、配置、索引、MCP、PGLite、Embedding 和维护机制。处理其他领域知识时，不得仅因执行知识库操作而检索该目录；只有问题本身涉及 GBrain，或者用户明确要求时才访问。

如果改用 `.gbrain/`，该规则应调整为：只有问题本身涉及 GBrain，或者用户明确指定具体文件时，Codex 才可通过本地文件系统读取；GBrain MCP 的常规 `search` 无法检索被文件扫描排除且未进入索引的内容。
