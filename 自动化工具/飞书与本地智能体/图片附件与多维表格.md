# 飞书—Codex 本地桥接：图片、附件与多维表格

[返回知识库导航](../../知识库导航.md)

> **重点：** 飞书中的图片默认只是当前聊天的视觉上下文；只有用户明确表达“修改、重绘、生成”等意图时才调用图像工具。附件和多维表格内容同样按 `chat_id` 隔离，不会跨聊天窗口混用。

<a id="core-conclusions"></a>
## 1. 核心结论

- 用户发送图片但没有修图或生图指令时，图片只作为上下文，用于识图、分析、写文案、提取信息或回答后续问题。
- 只有出现“修改这张图、把某物换色、重绘、生成图片、/image”等明确意图时，桥接才进入图像生成或编辑路径。
- 图片编辑默认基于当前窗口最近一次由用户上传的原图；不能因机器人曾生成过相似图片，就在生成图上反复迭代。
- 附件文本提取后进入当前 `chat_id` 的上下文；支持现代 Office、文本、PDF，并可借助本机 Office 兼容旧 DOC/XLS。
- 多维表格读取使用消息发送者本人 OAuth，不使用本机飞书用户身份；当前桥接实现为只读。
- 图片工具出现网络错误时，首次失败后重试 3 次，即最多尝试 4 次。

<a id="image-context-and-intent"></a>
## 2. 图片上下文与意图判断

<a id="image-analysis-vs-edit"></a>
### 2.1 图片分析与修图区分

收到图片时，桥接先保存原图并记录为当前聊天的视觉上下文，不立即调用图像工具。后续文字按语义判断：

| 用户表达 | 处理方式 |
|---|---|
| “帮我写这款产品的文案” | 读取图片并输出文字 |
| “这张图片里有什么” | 视觉分析 |
| “对比一下两张图” | 将两张图片作为上下文分析 |
| “把紫色手机壳换成黑色” | 基于用户原图修图 |
| “保持这只猫的画风，让它坐在月球” | 基于用户原图编辑/重绘 |
| `/image 一只戴宇航员头盔的橘猫` | 新图生成 |

不能仅因用户上传了一张图片就回复“正在依据原图重绘”。意图不明确时先按普通多模态对话处理；如果执行哪类动作确实无法判断，再向用户确认。

<a id="original-image-rule"></a>
### 2.2 用户原图优先规则

- 桥接分别记录“用户上传原图”和“机器人生成图”。
- 默认修图来源是当前聊天中最近的用户原图。
- 用户回复某条包含图片的消息时，优先使用被引用消息中的图片。
- 只有用户明确表示“在你刚生成的图上继续修改”，才允许使用机器人生成图。
- 每次编辑都要把实际参考图片随请求交给图像工具，不能只依赖文字描述或旧 session 中的模糊引用。
- 不同 `chat_id` 的图片不得互相引用。

这用于解决两个常见错误：把用户产品图误判为修图任务，以及在多轮编辑中偏离用户最初提供的参考图。

<a id="generation-retry"></a>
### 2.3 生成、重试与回传

1. 飞书图片由机器人身份下载到本机项目 `temp/`。
2. 桥接将明确的生成/编辑指令和参考图片交给 Codex 图像工具。
3. 图像工具成功后返回本地保存路径。
4. 桥接将图片上传并发回原聊天。
5. 若图像服务返回网络错误，首次失败后最多自动重试 3 次。
6. 全部失败时明确告知“图像生成服务网络异常”，不伪造成功结果。

约束：回传图片上限约 10 MB；长任务每 60 秒发送一次进度；心跳只证明桥接任务仍在运行；图片工具必须实际产出可访问的本地文件路径，桥接才能上传。文字对话与图像服务网络链路并不完全相同，文字正常不等于图像服务一定正常。

<a id="attachment-support"></a>
## 3. 附件读取

<a id="supported-formats"></a>
### 3.1 支持格式与限制

| 类别 | 扩展名 |
|---|---|
| Word | `.docx`、`.doc` |
| Excel | `.xlsx`、`.xls` |
| PDF | `.pdf` |
| 表格文本 | `.csv`、`.tsv` |
| 普通文本 | `.txt`、`.text`、`.log` |
| Markdown | `.md`、`.markdown` |
| 结构化文本 | `.json`、`.yaml`、`.yml`、`.xml` |
| 配置文本 | `.ini`、`.cfg`、`.conf` |

- 单个附件最大约 20 MB，提取文本最多约 30,000 字符；超出部分会截断并提示。
- 文件收到后保存为当前聊天附件上下文，下一条消息可直接要求总结、优化、核对或分析。
- 机器人必须引用实际提取到的文件名与内容；提取失败时不能假装已经阅读。
- 文件上下文按 `chat_id` 隔离，`/clear` 后清除当前聊天的附件引用。

<a id="pdf-ocr"></a>
### 3.2 PDF 文本与 OCR

PDF 优先提取可复制文本。扫描件没有有效文本时，用 Poppler 渲染页面，最多处理前 6 页，再交给 Codex 做 OCR 和理解。扫描质量、手写体、复杂表格和多栏排版会影响准确率；涉及金额、账号、日期等关键字段时应回看原页核验。

<a id="legacy-office"></a>
### 3.3 旧版 Office 文件

`.doc` 和 `.xls` 是旧二进制格式，常规 DOCX/XLSX 解析库不能直接稳定读取。桥接调用本机 Word 或 Excel 转为临时 DOCX/XLSX 后再提取，Office 自动化超时约 90 秒。因此旧格式支持依赖本机已安装且可正常启动 Microsoft Office；修复、登录、保护视图或格式确认弹窗都可能导致转换失败。

<a id="base-oauth"></a>
## 4. 多维表格与每用户 OAuth

<a id="app-capability-vs-user-auth"></a>
### 4.1 应用能力与用户授权

开发平台为自建应用添加多维表格能力和权限范围，只代表应用具备调用 OpenAPI 的资格，并不自动赋予访问每个用户私有表格的权限。访问具体 Base 还需要消息发送者完成个人 OAuth、本人拥有目标 Base 权限，并且授权身份与发消息账户一致。机器人身份负责聊天收发；用户身份负责读取用户私人资源。

<a id="per-user-profile"></a>
### 4.2 每用户授权配置

1. 用户在私聊发送 Base 链接或读取要求。
2. 桥接按发送者 `open_id` 生成独立 OAuth profile 名。
3. 未授权时返回飞书官方授权链接和二维码。
4. 用户用当前飞书账户完成授权。
5. 桥接校验授权后的 Open ID 必须与消息发送者一致。
6. 校验通过后用该 profile 读取用户可访问的 Base。

不使用电脑上的固定飞书用户替所有人访问，不在群聊执行用户私有 Base 读取，也不在知识库或日志记录 token、device code、App Secret 或具体 Open ID。`/clear` 不撤销 OAuth。

<a id="base-read-edit-limits"></a>
### 4.3 读取和编辑边界

为控制耗时和上下文体积，单次默认最多读取前 3 个数据表、每表前 100 条记录，汇总文本最多约 30,000 字符。超过上限必须说明截断，不能声称已经统计全量数据。

当前桥接只实现读取，没有实现 Base 写入。即使应用有写权限，也不能宣称机器人已经能修改数据。后续启用写入应采用“变更预览—用户确认—执行—记录结果”，默认只开放新增记录和更新字段；删除记录、字段、表、结构或权限必须单独确认。

<a id="context-lifecycle"></a>
## 5. 上下文生命周期

- 图片、附件、Base 摘要和 Codex session 都按 `chat_id` 保存。
- `/stop` 终止当前任务，但保留已有上下文。
- `/clear` 清除当前窗口的 Codex、图片、附件和 Base 内容上下文；下一条消息创建新 session。
- `/clear` 不影响其他窗口，也不撤销用户 OAuth profile。
- 上下文自动压缩时会提示用户；重要要求应在关键操作前重新声明。

<a id="verification"></a>
## 6. 验证清单

1. 上传产品图并说“帮我写文案”，确认只返回文字。
2. 再说“把紫色手机壳换成黑色”，确认使用用户原图。
3. 明确说“继续修改你刚生成的图”，确认此时才选择机器人生成图。
4. 上传 DOCX、XLSX、TXT、MD 和 PDF，确认回复引用实际内容。
5. 有本机 Office 时测试 DOC、XLS 转换；无 Office 时确认返回限制说明。
6. 私聊发送 Base 链接，确认首次进入每用户 OAuth。
7. 换另一个用户，确认不能复用前一用户授权。
8. 群聊发送私有 Base，确认拒绝读取。
9. 执行 `/clear`，确认内容上下文清除但 OAuth 保留。
