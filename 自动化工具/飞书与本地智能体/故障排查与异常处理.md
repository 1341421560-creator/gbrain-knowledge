<a id="core-conclusions"></a>
## 1. 核心结论

- 默认使用 `start-bridge.cmd`，不要直接运行可能被 PowerShell Execution Policy 拦截的 `start-bridge.ps1`。
- 启动成功需要两个长期进程：Node 桥接和 `lark-cli event consume` 事件消费者。
- 每 60 秒一次的进度消息表示本地任务还活着；图像服务最终仍可能因网络错误失败。
- `/status` 用于立即查看状态，`/stop` 用于终止当前聊天的任务，`/clear` 用于清空当前聊天上下文。
- 重复旧回复通过消息 ID 幂等、启动时间过滤和已处理缓存防止；`ignored startup replay` 通常是正常保护日志。
- 当前启动器没有固定写入 `http://127.0.0.1:7892`；桥接与子进程继承启动环境或系统网络设置。

<a id="startup-failures"></a>
## 2. 启动失败

<a id="powershell-policy"></a>
### 2.1 PowerShell 执行策略

典型错误是“无法加载文件 start-bridge.ps1，因为在此系统上禁止运行脚本”、`PSSecurityException` 或 `UnauthorizedAccess`。这不是桥接代码错误，而是 Windows 执行策略拒绝脚本。推荐：

```powershell
cd output/20260715_feishu_codex_bridge
.\start-bridge.cmd
```

也可双击 `start-bridge.cmd`。若一定要使用 PS1，应由用户自行评估并调整执行策略，不要为启动桥接随意降低全局系统安全设置。

<a id="process-and-websocket"></a>
### 2.2 进程与长连接

启动后应看到：

```text
[event] ready event_key=im.message.receive_v1
[source] feishu-websocket: connected
```

需要 Node 进程运行 `bridge.mjs`，同时 `lark-cli` 事件消费进程连接飞书 WebSocket。CMD 一闪而过时从终端运行以查看首个错误；有 Node 但无 connected 时检查登录、应用配置、长连接和网络；电脑重启后必须重新启动。避免同时打开多个桥接实例。

本机可承担桥接主机，但关机、睡眠、断网或退出进程都会离线；它不是高可用服务器。飞书开发平台订阅方式使用“长连接接收事件”。

<a id="slow-or-no-reply"></a>
## 3. 回复慢或没有回复

<a id="heartbeat-meaning"></a>
### 3.1 心跳代表什么

“Codex 仍在处理这条对话，桥接连接正常 (60s)”表示飞书到本地桥接回复通道可用、任务尚未结束、本地进程未退出。它不表示上游即将成功，也不保证最终返回图片。不同 `chat_id` 可以并行，某个聊天的长任务不会全局阻塞其他聊天。

<a id="stop-and-status"></a>
### 3.2 状态检查与停止

- `/status`：返回模型、运行时长、当前任务、队列、session、原图、附件和 Base 授权状态。
- `/stop`：终止当前 Codex 子进程并丢弃当前聊天待处理请求，保留此前上下文。
- `/clear`：终止任务并清除当前聊天的 Codex、图片、附件和 Base 内容上下文，不影响其他窗口。

若 `/status` 能立即响应，桥接主通道通常正常，问题更可能在当前任务或上游服务。若 `/status` 也无响应，检查进程、WebSocket 和事件权限。

<a id="image-failures"></a>
## 4. 图片生成与编辑失败

<a id="network-520"></a>
### 4.1 网络错误和 HTTP 520

“图像工具返回网络错误、未生成可保存路径”或 HTTP 520 表示图像服务未产出文件。当前会在首次失败后再重试 3 次，每 60 秒发进度，全部失败后明确报错。

- 文字成功不能证明图像服务网络正常，两者可能使用不同上游。
- 当前 CMD 未显式设置 `HTTP_PROXY`、`HTTPS_PROXY` 或 `ALL_PROXY` 为 `127.0.0.1:7892`。
- 桥接和 Codex CLI 继承启动进程环境及系统网络配置。
- 飞书上传是另一步：生成成功但上传失败，与图像服务无保存路径是两类故障。

排查顺序：在本机 Codex 测同类生图；查看日志究竟是 HTTP 520、超时、无路径还是上传失败；保持同一网络环境；先测试简单新图再测试带参考图编辑；连续失败时用 `/stop` 停止，避免无限占队列。

<a id="wrong-edit-source"></a>
### 4.2 引用错图或没有参考图

- 确认用户原图已成功下载且文件仍存在。
- 确认图片属于当前 `chat_id`，没有跨聊天引用。
- 回复图片消息时，确认桥接解析到被引用消息的图片。
- 修图调用必须携带真实文件，不能只依赖旧文字上下文。
- 默认用最近的用户原图；只有用户明确要求才使用机器人生成图。
- `/clear` 后图片上下文已清除，需要重新上传或引用。

如果用户上传图片只是为了写文案或分析，不应进入修图路径；这是意图分类问题，不是图像网络问题。

<a id="duplicate-and-replay"></a>
## 5. 重复回复、启动回放与撤回

<a id="idempotency"></a>
### 5.1 消息幂等与去重

飞书事件可能因断线重连、消费恢复或平台重投再次到达。桥接使用消息 ID、事件 ID/指纹、已处理缓存和任务状态防重。同一消息 ID 不应重复进入 Codex。若旧问题被再次回答，应记录 `chat_id`、消息 ID、时间和启动日志；不能只凭文本相同判断。

<a id="startup-replay"></a>
### 5.2 启动回放日志

```text
[bridge] processing om_xxx from oc_xxx
[bridge] replied to om_xxx
[bridge] ignored startup replay om_yyy from oc_xxx
```

`om_xxx` 是消息 ID，`oc_xxx` 是聊天 ID。`ignored startup replay` 表示桥接启动后收到发送时间早于本次启动的历史事件，已主动忽略以防旧问题重答。这通常是正常保护。只有新消息也被标成 replay 时才检查事件时间戳和本机时间。

<a id="recall"></a>
### 5.3 撤回消息

用户撤回后不应继续分析或回复。桥接会在开始处理、发进度和发最终结果前重新查询消息状态；已撤回则停止或丢弃回复。但已经实际发出的消息不会仅因源消息撤回而自动消失。

<a id="attachment-failures"></a>
## 6. 附件读取失败

| 问题 | 原因与处理 |
|---|---|
| 只看到内部 attachment 名 | 消息元数据未解析完整，应补取实际文件名 |
| DOCX/XLSX 没有被理解 | 检查是否成功下载并提取出文本 |
| DOC/XLS 失败 | 检查本机 Office、弹窗和 90 秒转换超时，或另存为新格式重发 |
| 扫描 PDF 没内容 | 检查 Poppler/OCR；默认最多前 6 页 |
| 文本乱码 | 转 UTF-8 或增加编码回退 |
| 大文件截断 | 拆分文件或指定范围；上限约 20 MB 和 30,000 字符 |

成功收到文件不等于成功读取内容。提取失败时必须说明原因和支持范围，不能假装已经阅读。

<a id="base-auth-failures"></a>
## 7. Base 授权或读取失败

1. 确认在私聊操作，群聊禁止个人 OAuth 读取私有 Base。
2. 确认应用已申请并发布必要权限。
3. 确认用户打开机器人发送的官方授权链接或二维码。
4. 确认授权账户就是消息发送者，且本人能访问目标 Base。
5. 检查 profile 与发送者 Open ID 的绑定校验。
6. 确认链接可解析出 Base token；Wiki 包裹链接要先解析真实资源。
7. 结果不完整时检查 3 表、每表 100 条和 30,000 字符限制。

`/clear` 不撤销 OAuth。切换账户应使用专门的注销和重新授权流程。

<a id="known-limitations"></a>
## 8. 已知边界

- 依赖电脑开机、网络正常和两个进程持续运行，不是云端高可用服务。
- 图像服务可能在桥接正常时单独失败。
- 上下文压缩后，旧消息逐字细节可能不完整。
- PDF OCR 默认最多前 6 页；Base 默认只读且有读取上限；旧 DOC/XLS 依赖本机 Office。
- 飞书撤回与本地处理存在竞态，无法保证已发出的回复自动撤销。

<a id="diagnostic-checklist"></a>
## 9. 诊断清单

1. 使用 `start-bridge.cmd` 启动。
2. 确认 Node 和 lark-cli 消费者都运行，日志有 `ready` 与 `connected`。
3. 飞书发送 `/status`，再发送简单文字“测试”。
4. 上传图片只要求描述，确认不误触发修图。
5. 用简单 `/image` 请求测试图像服务。
6. 上传 TXT 或 DOCX 验证附件提取。
7. 私聊发送 Base 链接验证用户 OAuth。
8. 检查日志中的 message_id、chat_id、重试、退出码和错误类型。
9. 运行 `node --check output/20260715_feishu_codex_bridge/bridge.mjs`。
10. 设置 `BRIDGE_TEST_MODE=1` 后运行 `node output/20260715_feishu_codex_bridge/bridge-tests.mjs`，确认 `Bridge regression tests passed.`。
