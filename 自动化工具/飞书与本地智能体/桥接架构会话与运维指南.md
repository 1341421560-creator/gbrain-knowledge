# 飞书—Codex 本地桥接：架构、会话与运维指南

[返回知识库导航](../../知识库导航.md)

<a id="core-conclusions"></a>
## 1. 核心结论

- 飞书端的每个聊天窗口以真实 `chat_id` 作为隔离键；同一窗口继承同一个 Codex session，不同窗口不会串上下文。
- 同一 `chat_id` 内严格顺序执行，不同 `chat_id` 可以并行；某个窗口长时间生图不会阻塞其他窗口。
- `/clear` 会终止当前任务并清除当前窗口的 Codex、图片和附件上下文；不会影响其他窗口，也不会撤销飞书 Base 用户授权。
- `/stop` 会真正终止当前 Codex 子进程并清空该窗口的待处理队列，但保留已有上下文。
- 当前文字模型为 `gpt-5.6-sol`，高推理强度，启用 fast service tier。
- 当前桥接已通过 Node 语法检查和本地回归测试；2026-07-28 核验时桥接 Node 进程和 `lark-cli event consume` 进程均在运行。

<a id="scope"></a>
## 2. 适用范围

- **适用对象：** Windows 本机上的飞书自建应用、`lark-cli`、Codex CLI 和 ChatGPT Pro 账户。
- **适用场景：** 在飞书私聊或群聊中进行文字问答、图片理解/生成/修改、文件分析以及私聊中的多维表格读取。
- **不适用场景：** 无人值守云服务、高可用生产集群、无需本机开机的全天候服务。当前电脑关机或桥接进程退出后，通道需要重新启动。
- **安全边界：** 不记录 App Secret、访问令牌、OAuth device code 或具体用户 Open ID；这些凭据只由本机 `lark-cli` 配置和凭据存储管理。

<a id="message-flow"></a>
## 3. 完整消息路径

<a id="event-receive-reply"></a>
### 3.1 事件接收与回复

完整路径如下：

1. 飞书用户向自建应用机器人发送消息。
2. `lark-cli event consume im.message.receive_v1 --as bot` 通过飞书 WebSocket 长连接接收事件。
3. `bridge.mjs` 将事件按 `chat_id` 放入独立队列。
4. 桥接识别消息类型：文字、富文本、图片、文件、多维表格链接或控制指令。
5. 普通文字通过本机 Codex CLI 创建或恢复对应 session。
6. 图片/附件先下载到项目 `temp/`，再作为上下文交给 Codex。
7. Codex 返回文字或生成的本地图片路径。
8. 桥接以机器人身份把文字或图片发送回原 `chat_id`。

事件消费者必须看到以下状态才算正常：

```text
[event] ready event_key=im.message.receive_v1
[source] feishu-websocket: connected
```

<a id="identity-boundaries"></a>
### 3.2 身份边界

| 操作 | 使用身份 | 说明 |
|---|---|---|
| 接收聊天事件 | bot | 自建应用机器人身份 |
| 发送回复、上传图片、下载聊天附件 | bot | 只处理机器人可见的聊天资源 |
| 普通文字/图像推理 | 本机 Codex CLI | 使用本机 Codex/ChatGPT Pro 登录态，不使用 OpenAI API Key |
| Base 读取 | 消息发送者本人 | 按发送者 `open_id` 建立独立 OAuth profile；不复用本机飞书用户 |
| Base 群聊访问 | 禁止 | 避免将个人数据直接暴露给群成员 |

<a id="sessions-context-queue"></a>
## 4. 会话、上下文与队列

<a id="chat-id-session"></a>
### 4.1 chat_id 与 Codex session

- 一个飞书聊天窗口对应一个 `chat_id`。
- 状态文件保存 `chat_id → Codex session_id` 映射。
- 同一窗口只要不执行 `/clear`，后续消息会恢复同一 Codex session。
- 图片、附件和 Base 提取内容也按 `chat_id` 保存，不会自动进入其他窗口。
- Codex 的原始 session 日志保存在用户目录下的 `.codex/sessions/`；桥接状态保存在项目 `temp/feishu-codex-bridge/state.json`。
- 当 Codex 自动压缩上下文时，桥接会提示：关键目标和结论已保留，但较早逐字细节可能不完整。

<a id="per-chat-queue"></a>
### 4.2 按会话隔离的并行队列

“按 `chat_id` 隔离”只改变执行调度，不改变上下文继承：

- 同一聊天窗口：严格按消息顺序执行，后一条消息等待前一条结束。
- 不同聊天窗口：可以并行执行，彼此不阻塞。
- `/stop` 和 `/clear` 属于即时控制指令，不必排在长任务后面。
- 队列隔离解决了“某个窗口生图十分钟，其他所有人都无法对话”的全局阻塞问题。

<a id="clear-stop-compaction"></a>
### 4.3 清除、停止与压缩

| 指令/事件 | 当前效果 |
|---|---|
| `/clear` | 终止当前任务、取消待处理请求、删除当前 `chat_id` 的 Codex session、图片和附件上下文；下一条消息创建新 session |
| `/stop` | 终止当前子进程、取消当前窗口待处理请求；保留已有 session、图片和附件上下文 |
| 用户撤回消息 | 桥接重新查询消息状态；已撤回则停止分析或回复 |
| 上下文压缩 | 保留摘要并主动提示用户；长期重要信息建议重新声明 |
| 启动回放 | 发送时间早于本次桥接启动时间的旧事件被标记为 `ignored startup replay`，防止重复回复 |

`/new` 曾短暂存在，但与 `/clear` 实际效果重复，现已移除。

<a id="model-performance-progress"></a>
## 5. 模型、速度与进度反馈

当前文字对话配置：

```text
model: gpt-5.6-sol
reasoning effort: high
service tier: fast
```

长任务反馈规则：

- 收到任务后立即发送“已收到，正在处理”。
- 后续心跳每 60 秒发送一次：`(60s)`、`(120s)`、`(180s)`……
- 文字对话、生图、修图和 Base 读取均使用相同的 60 秒心跳机制。
- 心跳只能证明桥接任务仍在运行，不保证上游图像服务一定会成功。

<a id="commands"></a>
## 6. 常用指令

| 指令 | 功能 |
|---|---|
| `/help` 或 `/帮助` | 显示常用指令和使用说明；不进入 Codex 队列，不消耗对话上下文 |
| `/status` 或 `/状态` | 显示桥接在线状态、运行时长、模型、当前任务、等待队列、session、原图、附件和 Base 授权状态 |
| `/stop` 或 `/停止` | 真正停止当前任务并清除当前窗口的排队请求；保留上下文 |
| `/clear` | 清除当前窗口上下文；不影响其他窗口 |
| `/image <描述>` | 生成一张图片 |
| 普通文字 | 继续当前 Codex session |
| 图片/文件 | 保存为当前窗口上下文，等待后续自然语言问题 |

<a id="startup-paths"></a>
## 7. 启动、关闭与路径

<a id="recommended-startup"></a>
### 7.1 推荐启动方式

PowerShell 可能因 Execution Policy 拒绝执行 `start-bridge.ps1`，因此推荐使用 CMD 启动器：

```powershell
cd output/20260715_feishu_codex_bridge
.\start-bridge.cmd
```

也可以在资源管理器中双击 `start-bridge.cmd`。启动脚本负责设置 Node、`lark-cli`、Codex CLI 和 Python 路径，然后运行 `bridge.mjs`。

不要把 `start-bridge.ps1` 作为默认入口，除非已经明确调整 PowerShell 执行策略。电脑重启、关机或桥接窗口退出后，需要再次运行 CMD；当前没有记录已配置 Windows 开机自启。

<a id="key-files-runtime"></a>
### 7.2 关键文件和运行数据

| 相对路径 | 用途 |
|---|---|
| `output/20260715_feishu_codex_bridge/bridge.mjs` | 主桥接程序 |
| `output/20260715_feishu_codex_bridge/start-bridge.cmd` | 推荐手动启动器 |
| `output/20260715_feishu_codex_bridge/start-bridge.ps1` | PowerShell 启动器，可能受执行策略限制 |
| `output/20260715_feishu_codex_bridge/attachment-extract.py` | DOCX/XLSX/PDF/文本提取 |
| `output/20260715_feishu_codex_bridge/attachment-convert.ps1` | 旧 DOC/XLS 的 Office 转换 |
| `output/20260715_feishu_codex_bridge/bridge-tests.mjs` | 回归测试 |
| `temp/feishu-codex-bridge/state.json` | session、图片、附件、Base 授权状态和消息去重状态 |
| `temp/feishu-codex-bridge/incoming/` | 飞书下载的图片和附件 |
| `temp/feishu-codex-bridge/ocr/` | PDF OCR 页面渲染 |
| `temp/feishu-codex-bridge/oauth/` | OAuth 二维码 |
| `temp/feishu-codex-bridge/bridge-stdout.log` | 桥接标准输出日志 |
| `temp/feishu-codex-bridge/bridge-stderr.log` | 事件消费和错误日志 |

启动 CMD 不需要为 Base/OAuth 新增变量。Base 用户 profile 复用现有 `lark-cli` 应用配置，运行时按用户创建。

<a id="verification-checklist"></a>
## 8. 验证清单

1. 执行 `node --check output/20260715_feishu_codex_bridge/bridge.mjs`。
2. 设置 `BRIDGE_TEST_MODE=1` 后运行 `node output/20260715_feishu_codex_bridge/bridge-tests.mjs`。
3. 确认测试输出 `Bridge regression tests passed.`。
4. 启动桥接后确认日志出现 `ready` 和 `connected`。
5. 飞书输入 `/status`，确认机器人能立即返回状态。
6. 发送普通文字，确认创建/恢复 session。
7. 必要时分别测试图片、文件和 Base 链接；不要用生产数据做破坏性测试。
